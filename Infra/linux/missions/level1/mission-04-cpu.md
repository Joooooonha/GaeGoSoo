# Mission 4 — CPU를 과도하게 사용하는 프로세스를 찾아라

**Level**: 1
**날짜**: 2026-09-11
**환경**: `gaegosoo` EC2, `ops-lab`

## 상황과 성공 기준

서버가 느려졌다. CPU가 실제 병목인지 관찰하고, 가장 많은 CPU를 사용하는 프로세스의 PID와 실행 명령을 찾아 근거를 제시하는 것이 목표였다.

## 관찰 → 조치 → 재검증

1. `uptime`에서 load average `1.00, 0.78, 0.39`을 확인했다. 최근 1분 값이 5분·15분 값보다 높아 최근 부하가 증가 중임을 알 수 있었다.
2. `top`의 `%Cpu(s)`에서 사용자 영역 CPU 사용률(`us`)이 30.5%였고, 프로세스 목록에서 PID `44614`의 `yes`가 `%CPU` 100.0을 사용하는 것을 확인했다.
3. `yes`는 출력을 무한히 반복하는 명령으로, 학습용 부하 프로세스임을 판단했다.
4. `kill 44614`로 기본 종료 신호(SIGTERM)를 보냈다.
5. `top`에서 `yes`가 사라지고 CPU 사용률이 낮아진 것을 확인했다. load average는 최근 평균이므로 즉시 0이 되지 않고 점차 감소하는 것도 확인했다.

## 개념 정리

- **CPU 사용률과 load average의 차이**: CPU 사용률은 CPU가 실제로 얼마나 바쁜지의 비율이다. load average는 실행 중이거나 CPU를 기다리는 작업(그리고 Linux의 끊을 수 없는 I/O 대기 작업)의 최근 평균 개수다. 전체 프로세스 개수가 아니다.
- **`uptime`**: 1분·5분·15분 load average를 보여 준다. 각각의 기간 동안 작업이 기다린 시간이나 처리 시간을 뜻하는 것이 아니라, 해당 기간의 최근 작업량 평균이다.
- **`top`**: 전체 CPU 요약과 프로세스별 `%CPU`를 실시간으로 보여 주는 외부 프로그램이다. 서버 전체 CPU 사용률과 특정 프로세스의 CPU 점유를 함께 관찰한다.
- **논리 CPU와 `%CPU`**: 단일 프로세스가 논리 CPU 하나를 꽉 사용하면 프로세스 행에는 100%로 나타날 수 있다. 코어가 여러 개라면 서버 전체 CPU 사용률은 그보다 낮게 보일 수 있다.

## 조치의 범위

이번 `yes`처럼 목적과 영향이 명확한 비업무·학습 프로세스는 PID를 확인한 뒤 `kill`로 종료해도 된다. 그러나 실제 Java 서비스가 높은 CPU를 쓰는 경우, 종료/재시작은 가용성을 일시 복구하는 **완화책**일 뿐 원인을 고치는 해결책은 아니다.

실제 서비스라면 종료하기 전에 가능한 한 다음 근거를 수집한다.

1. 최근 배포·트래픽·설정 변경이 있었는가
2. 애플리케이션 로그에 반복 오류가 있는가
3. 어떤 요청 또는 어떤 Java 스레드가 CPU를 쓰는가

이 근거로 무한 루프, 과도한 요청, 비효율 쿼리, 재시도 폭주 같은 원인을 고쳐야 재발하지 않는다. 상세한 Java 스레드 진단은 이후 심화 단계에서 다룬다.

## One-line takeaway

서버가 느려지면 `uptime`으로 load 추세를 보고, `top`에서 CPU 사용률과 고점유 프로세스를 확인한다. 명확한 비업무 프로세스는 PID로 종료한 뒤 프로세스·CPU·서비스 상태를 재검증하되, 실제 서비스의 재시작은 근본 원인 분석과 구분한다.
