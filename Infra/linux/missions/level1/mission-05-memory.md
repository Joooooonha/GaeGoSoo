# Mission 5 — 메모리 부족을 진단하라

**Level**: 1
**날짜**: 2026-09-11
**환경**: `gaegosoo` EC2, `ops-lab`

## 상황과 성공 기준

애플리케이션이 느려지거나 종료될 수 있는 메모리 압박 상황에서, 시스템 전체 메모리 여유와 프로세스별 실제 RAM 점유를 근거로 원인을 찾고 안전하게 복구한다.

## 관찰 → 조치 → 재검증

1. `free -h`에서 총 RAM 911MiB 중 `available`이 181MiB이고 swap이 없음을 확인했다.
2. `ps aux --sort=-%mem | head -n 8`으로 프로세스를 `%MEM` 내림차순으로 정렬했다.
3. PID `44918` Python 프로세스가 `%MEM` 28.8, RSS 268816KiB(약 262MiB)를 사용하고 있으며, `bytearray(256 * 1024 * 1024)`를 만든 뒤 잠든 상태임을 확인했다.
4. 학습용 비업무 프로세스임을 확인한 뒤 `kill 44918`로 종료했다.
5. `free -h`에서 `available`이 420MiB로 증가하고 Python 프로세스가 목록에서 사라진 것을 확인했다.
6. `curl localhost:8080/health`가 `OK`를 반환하는 것으로 서비스 정상 상태를 재검증했다.

## 개념 정리

- **`free`와 `available`**: Linux는 남는 RAM을 파일 캐시로 활용한다. `free`가 작아도 캐시를 회수할 수 있으므로, 새 작업을 swap 없이 시작할 수 있는 추정치인 `available`을 여유 판단의 중심으로 본다.
- **swap과 OOM**: swap이 있으면 RAM 부족 시 디스크를 임시 메모리로 쓸 수 있지만 성능은 크게 떨어질 수 있다. 이 서버는 swap이 없으므로, 심한 메모리 부족 시 Linux OOM Killer가 프로세스를 종료할 위험이 있다.
- **VSZ와 RSS**: VSZ는 프로세스가 확보하거나 매핑한 가상 주소 공간 크기이고, RSS는 실제 물리 RAM에 올라온 메모리다. 메모리 점유 원인 파악에는 RSS가 더 직접적인 근거다.
- **CPU와 다른 점**: Python 프로세스는 CPU 0.0%, 상태 `S`(sleep)이었지만 큰 RSS를 계속 유지했다. CPU를 거의 쓰지 않아도 메모리 압박 원인이 될 수 있다.
- **Java GC의 위치**: GC는 JVM 내부에서 Java 힙을 회수한다. Linux 운영 관점에서는 Java의 힙뿐 아니라 메타스페이스·스레드 스택·네이티브 메모리를 모두 합친 프로세스 RSS와 시스템 전체의 여유 메모리를 관찰한다.

## One-line takeaway

메모리 문제가 의심되면 `free -h`의 `available`과 swap을 확인하고, `%MEM`·RSS가 큰 프로세스를 찾아 안전성을 확인한 뒤 조치한다. 종료 후에는 메모리 여유와 서비스 health endpoint를 모두 재검증한다.
