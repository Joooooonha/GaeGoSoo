# Mission 3 — 실행 중인 프로세스를 찾아라

**Level**: 1
**날짜**: 2026-09-11
**환경**: `gaegosoo` EC2, `ops-lab` (GET `/health`)

## 상황

`/health` API가 응답하지 않았다. 파일이 존재하는지와 서비스가 실제로 실행 중인지가 별개임을 전제로, Linux의 Process 관점에서 원인을 진단했다.

## 관찰 → 조치 → 재검증

1. `pgrep -fa java`로 Java 프로세스를 찾았지만 결과가 없었다.
2. `ps`에서 현재 SSH 셸(`bash`)과 관찰 명령(`ps`)만 보이는 것을 확인했다. `ps`는 현재 셸에 연결된 프로세스를 간단히 보며, `pgrep -fa java`는 Java 프로세스를 좁혀서 찾는 데 적합하다.
3. Java 프로세스가 없으므로 Spring Boot 서비스가 실행되지 않았다고 판단했다.
4. `nohup java -jar app.jar > app.log 2>&1 &`로 서비스를 재기동했다.
5. `pgrep -fa java`에서 `44410 java -jar app.jar`를 확인하고, `curl localhost:8080/health`가 `OK`를 반환하는 것으로 복구를 검증했다.

## 개념 정리

- **프로그램과 프로세스**: `app.jar`는 디스크에 있는 실행 산출물이고, Java가 이를 메모리에 올려 실제로 실행 중인 상태가 Process다. 파일이 남아 있어도 프로세스는 없을 수 있다.
- **PID**: Linux가 프로세스마다 부여하는 고유 번호다. 백그라운드 기동 시 표시된 `[1] 44410`에서 `[1]`은 현재 셸의 작업 번호, `44410`은 실제 PID였다.
- **`pgrep -fa java`**: `-f`는 프로세스 이름뿐 아니라 전체 실행 명령에서 `java`를 찾고, `-a`는 PID와 전체 실행 명령을 함께 표시한다.
- **기동 명령의 셸 문법**: `nohup`은 SSH 종료 신호를 무시하게 하고, `>`는 표준 출력(파일 디스크립터 1)을 `app.log`로 보낸다. `2>&1`은 표준 오류(2)를 표준 출력(1)이 향하는 곳과 같게 하며, 마지막 `&`는 명령 전체를 백그라운드에서 실행한다.

## 다음 진단 분기

Java 프로세스가 **없는** 경우에는 기동 실패·종료를 우선 의심하고, 재기동 후 프로세스와 health endpoint를 검증한다.

Java 프로세스가 **있는** 경우에는 곧바로 정상이라고 결론 내리지 않는다. 다음에는 로컬 health endpoint, 포트가 실제로 열려 있는지, 애플리케이션 로그를 차례로 관찰해 프로세스·애플리케이션·네트워크 중 어느 층의 문제인지 구분한다.

## One-line takeaway

API 응답이 없으면 먼저 Java 프로세스의 실행 여부를 확인하고, 결과가 없으면 재기동한 뒤 프로세스와 health endpoint로 복구를 검증한다.
